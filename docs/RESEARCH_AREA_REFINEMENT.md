# Research area catalog and course-specific categories

Implemented 2026-10-25 for the confirmed local development `rms_db`.

The existing module is retained: one `research_projects.category_id`, category/area pairs in `category_research_areas`, and multiple project associations in `research_project_areas`. Existing checkbox forms, version snapshots, administrator page, authentication, CSRF, eligibility, ownership, draft locks and audit logging are reused. No new framework, program partition, category record or replacement proposal table was introduced.

## Changes and files

- `database/migrations/031_curated_bsit_bscs_research_areas.sql`: adds `research_area_selection_scope` with one row per scoped area, curated label, enabled flag and ordering; PK/FK protects stable area references and an index supports scope selection.
- `database/schema/rms_db.sql`: synchronizes fresh installations, including safe drop order for the new child table.
- `scripts/migrate.php`: adds the structural/seed-completion verifier for migration 031.
- `includes/research-workflow.php`: reuses catalog/validation helpers with scope checks and optional server-loaded saved associations.
- `pages/researcher/submit-research.php`, `pages/researcher/edit-research.php`: reuse existing forms, transactions, area persistence and title workflow; expose curated labels and preserve saved/legacy selections.
- `js/research-area-picker.js`: dynamically filters options by category, keeps selected mismatches visible, prevents a sixth selection, reports empty/mismatched groups and never automatically clears an area.
- `pages/admin/admin-research-areas.php`: existing complete catalog now manages selection scope and display labels alongside names, descriptions, activation and category mappings.
- `docs/testing/manual-reports/2026-10-25-research-areas-01.md`: actual static/database evidence and pending browser checks.

## Preservation and migration behavior

Seven equivalent catalog records are reused. Their canonical names and codes remain unchanged; more specific proposal labels live only in the scope table. Thirteen distinct areas are added. Combined web/mobile (RA007), database/information-systems (RA008), and transformation/e-governance (RA036) entries remain intact; their distinct specializations receive separate IDs.

The migration never modifies proposal associations or research/version/review rows. It initializes the suggested category mappings only for an area newly entering the scope. Existing mappings for those seven reused areas are adjusted to the requested defaults; mappings for the other 33 original areas remain intact for administration/history. Removing a category mapping never removes a project association.

Rerunning the runner skips the tracked migration. Direct SQL replay with unchanged catalog identities inserts no duplicate names and finds no new scope entries, preserving administrator labels, enabled flags and mapping edits. Canonical area names are editable catalog data: use the runner rather than bypassing its ledger after renaming catalog records.

New area codes are allocated above the current numeric RA maximum; IDs are generated by the database, never inferred from the user's list numbers. The following IDs are the actual verified local results; upgraded installations with additional catalog records can allocate different new IDs/codes.

## Course-specific classification (migration 044)

- `database/migrations/044_course_specific_research_categories.sql` adds seven categories, 38 distinct areas, 40 category-area links, and the `research_category_programs` mapping for BSCS/BSIT.
- Student category options and server validation use the authenticated account's active program. Faculty continue to use the unscoped legacy categories and mappings.
- Legacy catalog rows and project links are preserved. Students editing an older project can retain its saved category and areas, but cannot add new areas under a legacy category.
- `database/schema/rms_db.sql` contains the same catalog for fresh installs, and `scripts/migrate.php` verifies the migration's schema and seeded mappings.

## Editing historical classifications

Saved junction-table areas are loaded even when inactive, excluded from scope, or unmapped. They can remain under the original category. A category change must validate every selected area against the current category and enabled scope. Users must explicitly uncheck mismatches; removing a saved association requires the removal-confirmation checkbox. Validation is repeated after locking the owned editable project. Legacy free-text classification is displayed and preserved separately.

The one-to-five limit and duplicate checks apply on the server. The picker uses JavaScript for category-based area filtering; server validation remains authoritative and rejects invalid combinations.

## Deployment and rollback

Migration 031 was applied only to local development `rms_db`, through `php scripts/migrate.php apply 031_curated_bsit_bscs_research_areas.sql`. Migration 044 was applied to the same local database on 2026-10-29 through the runner after backing up the affected catalogs, mappings, project-area links, and ledger to the ignored `backups/research-course-catalog-20261029.sql.backup`; the pre-migration hashes are in `backups/research-course-catalog-20261029-baseline.json`. Migration 010 and unrelated pending migrations were not run or reconciled.

For another installation, inspect its target/catalog/ledger and back up affected data before applying the applicable migration with the runner. Apply database changes before serving the updated PHP. Do not import the canonical fresh-install schema into an existing database.

Rollback requires coordinated code/database review. Prefer disabling scope entries through the administrator page. Do not delete new catalog rows that may now have proposal links; never restore an old full-table backup over subsequent work without reviewing data changes. No automatic rollback or cleanup was performed.
