## File layout and integrity

The server-controlled root is `storage/earist/`. Root, `scratch/` and `generated/` have unconditional `Require all denied` guards, plus a project-root rewrite denial. Runtime content is ignored by Git while protection files remain visible to source control. The user confirmed Incognito and signed-in Admin 403 responses for the retained synthetic primary file; other HTTP paths and future authenticated download routes remain unverified. The service rejects missing/changed guards, unexpected roots and canonical path redirects.

Every scratch allocation creates a separate random directory and random `.tmp` file. Cleanup removes only that allocation's known regular file and empty directory after checking directory identity; it never recursively deletes or enumerates another request's files. A changed allocation or nonempty abandoned directory is retained and reported. Default old synthetic renderer callers still use OS scratch; live callers must explicitly use the configured protected scratch option.

`earistDocumentValidateDocx()` checks compressed size, entry/uncompressed limits, duplicate and unsafe names, encryption, every entry's bytes/CRC, all `.xml`/`.rels` parsing without entity/network resolution, required DOCX parts/body/content types, relationship sources/targets/IDs and XML relationship references. Approved external relationships are retained and counted, never fetched. This is not a full OOXML schema validator or a Word-layout/printing check. The application must still render only from approved templates and validated authorized mappings.

`earistDocumentStoreOutput()` is an internal file primitive with no authentication or SQL. The Faculty generation service authorizes the owner and reviewed draft, validates the entire primary/companion set, then calls it inside its history transaction. It allocates a new exclusive random `generated/<64-hex-id>/` directory, writes/flushed/synchronizes files, rechecks disk hashes/sizes/package structure and writes `manifest.json`. Existing paths are never reused. Failed writes retain only private partial allocations; no deletion API is provided.

Each set manifest records its version, set ID, document type and primary/optional QSF companion paths, hashes, sizes and safe server filenames. `earistDocumentManifestFile()` rejects mixed-set references and companions on non-QSF forms. The implemented generation service stores this manifest in immutable `snapshot_json`; the primary reference must agree with the generated-history row's DOCX columns. File persistence alone is not a successful document/history version.

`earistDocumentOpenFile()` accepts only a manifest reference after authorization. It rejects traversal, URLs, absolute/alternate-stream paths and canonical link/junction escapes, opens/locks a regular file, checks size/hash and rewinds the same handle for its caller. The Faculty download route validates the current Faculty owner, generated row, draft, source, complete manifest and integrity before sending attachment/no-store/nosniff headers and streaming that same handle. A missing or corrupt historical file produces an unavailable state; it is never silently rendered again.

## SQL/file publication and interruptions

Migration 052 remains unchanged. Faculty generation binds each file set to the current owner, draft revision, source fingerprint, renderer/template/binding versions, exact reviewed payload and warning acknowledgment. Repeated tokens return the authorized committed version; new requests lock the parent source and allocate a unique version. Pages accept no filesystem path or caller-supplied owner. The separate Admin Annex D implementation uses the same publication transaction while retaining distinct Admin document ownership and Faculty source ownership.

SQL and filesystem changes cannot commit atomically. The current sequence validates the rendered package set before opening the transaction, rechecks and locks the account/source/draft, stores the validated files, then commits immutable success metadata. On failures or ambiguous commits, retain the random file set and reconcile against authoritative history/request hashes before a retry. Replaying a committed request returns its existing authorized version, not a new version or overwritten bytes. Transactional persistence/concurrency is not verified against a database because no isolated disposable DB is available.

For a future interrupted request, an authorized operator should pause generation, preserve logs/metadata without document contents, and determine whether a committed history snapshot references the set. Check both primary and companion hashes and the source/draft/owner identifiers. Referenced files are history and must be retained. Unreferenced/partial sets remain private pending an explicit case-specific retention decision. Age or filename alone does not prove that a request is inactive or that removal is safe. No automatic sweep, recursive cleanup or age-based retention is installed.

## Coordinated backup and recovery

Existing Admin backup produces SQL snapshots only. It does not capture DOCX or companions and is not sufficient for this feature.

Before real-record use, establish this operator procedure:

1. Pause new EARIST generation and complete or record in-flight publications. Preserve the generation configuration and templates/binding manifest/renderer revision needed to interpret history; do not rewrite originals.
2. Obtain a separately authorized consistent SQL backup including both Migration 052 tables and their referenced research/users. Use supported backup tooling; never expose database credentials in a command/report.
3. Copy the complete immutable `generated/` root, file manifests and required source/configuration metadata to protected backup storage. Preserve ACLs or re-establish equivalent privacy at the destination. Do not copy active scratch as if it were valid history.
4. Cross-check every backed-up history reference, primary/companion size/hash and manifest association. Record completion, nonzero sizes and backup hashes privately. Retain unreferenced evidence separately. Missing references mean an incomplete backup, not permission to regenerate history.
5. Resume generation only after the coordinated backup is complete. Keep versions indefinitely by default until an institution-approved retention policy exists; no deletion schedule is implied.
6. Test restoration only with explicit authorization to a verified isolated disposable database and private file root. Never restore over normal `rms_db`, overwrite live history or assume a database name proves isolation. Verify references and role boundaries without fabricating sessions or test hooks. A file/hash check is not a restore rehearsal.

No backup/export, external copy, database restore, deletion or retention job was executed by Step 1. Backups themselves require the same privacy controls as generated documents.
